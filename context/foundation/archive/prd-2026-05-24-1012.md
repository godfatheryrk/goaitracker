# GOAITracker — Product Requirements Document

## Vision & Problem Statement

A person pursuing a personal venture (a goal with multiple component steps and out-of-pocket costs) today has no single place that holds both the plan and the running cost. They reach for a spreadsheet (cost-friendly, plan-hostile), a notes doc (plan-friendly, cost-hostile), or a team-oriented project tool (built for shared workflows, not solo personal goals). The two pains compound: at the start of a venture the user faces a blank page and doesn't know what steps to take (decision paralysis); mid-flight, the data they do produce — progress, receipts, partial sums — is trapped across surfaces, with no unified view of "where am I and what has it cost me so far?". Both pains kill momentum within weeks.

The insight that makes this product worth writing: an AI that proposes the initial step list from a short venture description converts the blank page into a starting plan the user can edit, which is the cheapest possible lever against decision paralysis. Status-quo tools are empty containers — they assume the user already has the plan. GOAITracker generates the plan, lets the user shape it, and keeps step-progress and cost in a single per-venture view.

## User & Persona

Single primary persona. The founder is the first user and tester — someone who pursues personal ventures (their own goals, not team projects) and needs both a step plan and a per-venture cost ledger in one place. Solo use; no shared workspaces; data is per-user.

## Success Criteria

### Primary

- At least 3 of the 5 AI-suggested steps are still present (in any state — kept verbatim or edited) in the user's saved venture plan. Measures that the AI suggestion was useful enough to reduce — not just trigger — manual editing. Absolute count is preferred over a ratio because the AI suggestion cap is fixed at 5 per FR-008; the threshold is the rounded-up 50% of that cap (≥ 50% from AI, from the seed).

### Secondary

- Users return to a venture at least once after creating it. A weak proxy for "the product became part of their workflow" rather than a one-off blank-page reliever.

### Guardrails

- A user can NEVER see another user's ventures, steps, or expenses. Per-user data isolation is load-bearing; a bug here is a privacy incident even if everything else works.
- AI failures stay invisible to the user as failures. If the AI suggestion is unavailable for any reason, the user can still create a venture and add steps manually — the AI is an enhancement, not a hard dependency.
- Editing a venture, step, or expense feels instant (≤ ~1s perceived latency on the editing actions). Manual editing is the core loop; slowness breaks the workflow-friction promise.
- No accidental data loss on edit/delete. Venture and step removal need confirmation (or undo). Personal-venture data is hard to recover — a misclick that drops a 12-step plan is a product failure.
- If sharing of ventures is added in a future version, the privacy isolation guardrail must continue to hold — users only see their own ventures unless explicitly shared.

## User Stories

### US-01: User creates their first venture end-to-end

- **Given** a registered user has signed in
- **When** they create a new venture by entering a title and a short description
- **Then** the app responds with an AI-suggested list of up to 5 steps that the user can keep, edit, add to, or remove

#### Acceptance Criteria

- AI returns no more than 5 steps for a single venture
- AI failure (timeout, provider error) does NOT block venture creation — the user gets an empty step list and a non-blocking notice, and can continue manually
- After AI returns, the user can add / edit / delete steps without further constraint
- The user can optionally add one or more expenses to the venture (amount + short description + date); leaving expenses empty is valid
- The user can toggle each step's completion state and immediately see the updated proportion of completed-vs-total steps and accumulated total cost on the venture view
- All data created in this flow is visible only to the user who created it

## Functional Requirements

### Authentication

- FR-001: User can register an account with email + password. Priority: must-have
  > Socratic: Counter-arguments considered ("email/password infrastructure is heavier than it looks"; "open registration + AI calls is an abuse vector"). Resolution: stands as written — seed explicitly calls for "simple user account system"; abuse mitigation captured separately as NFR (registration cannot be exploited to burn AI budget).
- FR-002: User can sign in with email + password. Priority: must-have
  > Socratic: Counter-arguments considered ("password recall is the #1 reason users abandon personal apps"; "this FR collapses into FR-001 if auth model changes"). Resolution: stands as written — standard sign-in pattern; session-length tuning is downstream.
- FR-003: User can sign out. Priority: must-have
  > Socratic: Counter-arguments considered ("rarely used on single-device apps"; "load-bearing for shared-device privacy"). Resolution: stands as written — privacy guardrail is load-bearing; sign-out is cheap.

### Ventures

- FR-004: User can create a new venture by entering a title and a short description. Priority: must-have
  > Socratic: Counter-arguments considered ("short description is too vague — AI quality depends on input richness"; "venture creation should also let user set goal/deadline/scope upfront"). Resolution: stands as written. UX commitment: the create-venture surface will display a hint that better descriptions yield better AI suggestions, nudging users to be richer without imposing hard input constraints.
- FR-005: User can view a list of all their own ventures. Priority: must-have
  > Socratic: Counter-arguments considered ("flat list won't scale past ~10 ventures; will need filter/sort/search"; "active vs completed should be visually separated"). Resolution: stands as written — list view is v1; filter/sort/separation are v2 concerns once usage volume justifies them.
- FR-006: User can open a single venture and see its details (description, steps, expenses, progress, total cost). Priority: must-have
  > Socratic: Counter-arguments considered ("single screen risks cognitive overload, especially on mobile"; "showing description creates expectation that editing it re-runs AI"). Resolution: stands as written — this unified view IS the product's core insight; editing the venture description was dropped from v1, which neutralises the second concern.
- FR-007: User can delete a venture (with confirmation). Priority: must-have
  > Socratic: Counter-arguments considered ("hard delete loses irreversible work — should be soft delete / archive"; "delete is rare for personal goals — most users want 'mark abandoned' / 'archive'"). Resolution: stands as written — confirmation dialog covers the guardrail; archive semantics deferred to v2.

### Steps (AI-suggested + manual)

- FR-008: User can receive an AI-suggested step list (max 5 steps) one-shot when creating a venture. Priority: must-have
  > Socratic: Counter-arguments considered ("one-shot with no regenerate = bad first suggestion = bad venture forever"; "5-step cap is arbitrary — some ventures need 15+ steps"; "5-step cap pressures AI toward broad/unactionable suggestions"). Resolution: stands as written — one-shot + cap is the cheapest viable AI surface for v1; tune later based on Primary metric data (≥ 3 of 5 AI step retention).
- FR-009: User can manually add a new step to a venture. Priority: must-have
  > Socratic: Counter-arguments considered ("manual adds let users bypass AI entirely, diluting the Primary metric"; "no upper bound risks ballooning past the AI cap's UX purpose"). Resolution: stands as written — manual editing is essential; the Primary metric is defined on AI-suggested steps only (denominator fixed at 5), so manual adds do not dilute it.
- FR-010: User can edit a step's text. Priority: must-have
  > Socratic: Counter-arguments considered ("editing AI step text muddies whether it still counts toward Primary metric"; "delete+re-add could replace edit but loses completion state"). Resolution: stands as written — edit preserves completion state, which delete-recreate does not; an edited AI step still counts toward the Primary metric (any state — kept verbatim or edited).
- FR-011: User can delete a step (with confirmation). Priority: must-have
  > Socratic: Counter-arguments considered ("deleting AI steps reduces the Primary metric count toward the ≥ 3 threshold"; "per-step confirmation is friction overkill; undo would be cheaper"). Resolution: stands as written — the metric explicitly excludes deleted steps; UX choice (confirmation vs undo) is a downstream design decision.
- FR-012: User can mark a step as complete and toggle back to incomplete. Priority: must-have
  > Socratic: Counter-arguments considered ("toggle invites misclick that resets celebration; binary done/not-done is simpler"; "completion needs more states than binary — in-progress / blocked / done carry more signal"). Resolution: stands as written — binary is the simplest signal supporting the progress view (FR-015); richer states are v2.

### Expenses (optional, venture-level)

- FR-013: User can add an expense to a venture (amount + short description + date). Priority: must-have
  > Socratic: Counter-arguments considered ("expenses without currency / category are too thin"; "if usage is <30%, cut expenses for v2 instead of v1"; "venture-level lumps distinct cost categories — users wanting per-step costs hit a wall"). Resolution: stands as written — per the scope-down, expenses are optional and lightweight; richer expense model is v2; currency choice is a downstream concern.
- FR-014: User can delete an expense. Priority: must-have
  > Socratic: Counter-arguments considered ("delete-only after dropping edit means typo fix needs deleting + re-typing all fields"; "expense delete should be soft / undo-able"). Resolution: stands as written — tension with the edit-an-expense drop acknowledged; users with frequent typos can revisit the edit decision in v2; soft-delete is overkill for the lightweight expense model.

### Progress view

- FR-015: User can see the proportion of completed vs total steps on a venture. Priority: must-have
  > Socratic: Counter-arguments considered ("proportion is wrong shape for small-N ventures — each step = 20% jump; N-of-M is clearer"; "single-venture progress is detail-page noise — cross-venture dashboard is what users actually check"). Resolution: stands as written — concrete shape (bar vs N-of-M) is downstream design; cross-venture dashboard is v2.
- FR-016: User can see the accumulated total cost of all expenses on a venture. Priority: must-have
  > Socratic: Counter-arguments considered ("total cost is meaningless without a budget to compare against"; "no currency awareness breaks the total for multi-currency users"). Resolution: stands as written — passive total is the cheapest unified-view signal; budget comparison is v2; currency handling is downstream.

## Non-Functional Requirements

- A user is never able to observe another user's ventures, steps, or expenses via any product surface.
- When the AI step suggestion is unavailable for any reason, venture creation completes and the user can add steps manually within the same session.
- Editing a venture, step, or expense produces visible user feedback within ~1 second of the user's action.
- Destructive actions on a venture or step (delete) cannot complete without an explicit second user gesture (confirmation or in-window undo).

## Business Logic

Given a short description of a personal venture, the app produces a short actionable plan (≤ 5 steps) the user can edit and track alongside the cost of pursuing it.

The input is what the user types when they create a venture — a title and a free-text description of what they want to accomplish ("learn welding", "renovate the bathroom", "ship a side project"). Richer descriptions produce better plans; the create-venture surface signals this expectation to the user.

The output is a one-shot ordered list of at most five steps that the user can keep, edit, augment with manual steps, or delete. The plan never re-generates after creation — the user owns it from that point on. If the suggestion is unavailable, the venture is still created with an empty step list and the user proceeds manually; the rule degrades to "no AI input" rather than failing the venture creation entirely.

The user encounters the plan immediately on the new-venture detail view, where it sits alongside the running expense ledger and the live progress signal (proportion of steps completed; total accumulated cost). The same view is what the user returns to over the lifetime of the venture — the unified plan-plus-cost surface is the place the product lives.

## Access Control

Multi-user web app with email + password login. Each user has an account; data is per-user and not shared. Flat role model — every user has identical capabilities and can only see/edit their own ventures, steps, and expenses. Unauthenticated users hitting any gated route are redirected to sign-in.

## Non-Goals

- **No file-format exports** (CSV / PDF / spreadsheet reports of venture data). Explicitly excluded in the seed; users still export to spreadsheet today if they want a report.
- **No deadline / time-based reminders or notifications** about venture or step due dates. Explicitly excluded in the seed; the app is pull-based, not push.
- **No sharing of ventures with other users.** Explicitly excluded in the seed. Forward-compatibility note: if added in a future version, the privacy isolation NFR (a user cannot observe another user's ventures unless explicitly shared) must continue to hold.
- **No AI-generated step-execution hints** (i.e. the AI does NOT explain HOW to perform a step). Explicitly excluded in the seed. The AI's only role is generating the initial step plan from the venture description.
- **No multi-currency support.** Expenses are recorded in a single currency; cross-currency conversion is v2.
- **No per-step expense allocation.** Expenses are venture-level only, not tied to individual steps; per-step expense allocation is v2.
- **No cross-venture dashboard or progress roll-up** across all of a user's ventures. Each venture is viewed individually; an across-ventures view is v2.
- **No "regenerate AI suggestion" button.** AI runs ONCE at venture creation, never again. Reinforces FR-008 scope.
